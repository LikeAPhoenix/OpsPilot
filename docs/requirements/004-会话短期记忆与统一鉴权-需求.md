# 1. 背景（Why）

当前聊天链路只有进程内内存会话窗口，服务重启后历史会丢失，也没有用户登录和统一鉴权能力。这样既无法支撑多用户隔离，也无法为连续对话提供稳定的短期记忆。因此需要引入账号体系、JWT 统一鉴权，以及基于 Redis 的“滑动窗口 + 摘要”会话短期记忆。

# 2. 目标（What，必须可验证）

- [ ] 提供本地最小可用账号体系，支持注册、登录和 JWT access token 鉴权
- [ ] 除 `/api/auth/*` 外，所有业务接口统一接入 JWT 中间件
- [ ] 聊天接口支持 `sessionId` 可选，首轮可由服务端自动创建会话
- [ ] 会话短期记忆改为 Redis 持久化，采用“最近轮次 + 摘要”策略
- [ ] 超过配置阈值后触发摘要压缩，但不能在第 7 轮时丢失对话

# 3. 非目标（Explicitly Out of Scope）

- 不引入 refresh token、角色权限、多租户
- 不接入外部认证中心
- 不将摘要内容写入知识库、Milvus 或文档目录
- 不新增健康检查、管理后台或用户资料维护接口

# 4. 使用场景 / 用户路径

1. 用户调用 `/api/auth/register` 注册账号。
2. 用户调用 `/api/auth/login` 获取 JWT access token。
3. 用户访问 `/api/chat` 或 `/api/chat_stream` 时携带 `Authorization: Bearer <token>`。
4. 首轮聊天可不传 `sessionId`，服务端自动创建会话并返回 `sessionId`。
5. 后续轮次复用同一 `sessionId`，系统从 Redis 读取摘要和最近轮次拼装上下文。
6. 当会话轮次数超过阈值时，系统先生成新摘要，再裁剪最近轮次。

# 5. 功能需求清单（Checklist）

- [ ] 新增 `/api/auth/register` 和 `/api/auth/login`
- [ ] 新增 MySQL 用户表 `users`
- [ ] 新增 `pkg/auth`，封装 JWT claims、签发、解析、校验
- [ ] 新增 `pkg/snowflake`，统一生成 `userId` 和 `sessionId`
- [ ] 新增 JWT Gin 中间件，位置固定在 `internal/interfaces/http/middleware`
- [ ] `chat`、`chat_stream`、`upload`、`ai_ops` 全部挂到统一 JWT 中间件下
- [ ] `chat`、`chat_stream` 的 `Id` 改为可选；普通聊天响应新增 `sessionId`
- [ ] `chat_stream` 在首个正文分片前发送 `session` SSE 事件
- [ ] Redis 会话仓储保存会话元数据、最近轮次、TTL 和会话锁
- [ ] 默认保留最近 6 轮，压缩阈值 9 轮，第 10 轮后才触发摘要压缩
- [ ] 摘要失败时不裁剪历史轮次，避免真实数据丢失

# 6. 约束条件（非常关键）

- 技术约束：继续使用 Gin、GORM、Redis 和现有 Eino 能力，不引入新的 Web 框架
- 架构约束：JWT 基础能力放 `pkg/auth`，Gin 中间件放 `internal/interfaces/http/middleware`
- 边界约束：HTTP 鉴权细节不能下沉到 `application`，登录流程不能放进 `pkg`
- 安全约束：不得把真实密钥、真实 DSN、真实租户信息写入代码或文档
- 行为约束：第 1 到第 9 轮必须保留明细；第 10 轮才允许触发摘要压缩

# 7. 可修改 / 不可修改项

- ❌ 不可修改：现有业务接口路径、工具注册名称、AIOps 和知识库业务语义
- ✅ 可调整：聊天应用服务签名、会话仓储抽象、启动装配逻辑、配置结构、示例程序

# 8. 接口与数据约定（如适用）

- `POST /api/auth/register`
  - 入参：`username`、`password`
  - 出参：`userId`、`username`
- `POST /api/auth/login`
  - 入参：`username`、`password`
  - 出参：`userId`、`accessToken`、`expiresAt`
- `POST /api/chat`
  - 入参：`Id` 可选、`Question` 必填
  - 出参：`answer`、`sessionId`
- `POST /api/chat_stream`
  - 入参：`Id` 可选、`Question` 必填
  - SSE 事件：`connected`、`session`、`message`、`done`
- Redis 键结构：
  - `opspilot:session:meta:{sessionId}`
  - `opspilot:session:turns:{sessionId}`
  - `opspilot:session:lock:{sessionId}`

# 9. 验收标准（Acceptance Criteria）

- 如果执行 `go test ./...`，则仓库编译和测试通过
- 如果未携带 JWT 访问业务接口，则返回 `401`
- 如果用户访问不属于自己的 `sessionId`，则返回 `403`
- 如果第 7 轮继续聊天，则不会触发摘要压缩，也不会丢失历史明细
- 如果写入第 10 轮，则会先生成新摘要，再把最近轮次裁剪到 6 轮
- 如果摘要生成失败，则会话轮次不被裁剪
- 如果 MySQL、Redis、JWT secret 或 Snowflake 节点配置不可用，则启动阶段直接失败

# 10. 风险与已知不确定点

- 会话锁覆盖单次聊天处理路径，会增加同一会话并发请求的冲突概率
- 摘要压缩依赖模型输出质量，若摘要过于粗糙，可能影响后续对话连续性
- `upload` 和 `ai_ops` 虽接入统一鉴权，但本期不扩展细粒度权限控制

# 11. 非目标

- 不实现用户注销、刷新 token、修改密码
- 不实现会话分享、会话归档、长期记忆
- 不把短期记忆扩展到 AIOps 或知识库索引链路
