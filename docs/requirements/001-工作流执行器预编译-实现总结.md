# 001-工作流执行器预编译-实现总结

## 1. 实现了什么

本次实现将 `internal/ai/workflows` 下的三个核心工作流从“请求时构建执行器”调整为“启动时构建执行器、运行时复用”：

- `chat` 工作流在 `NewWorkflow(ctx, config)` 阶段预编译 `compose.Runnable`
- `knowledgeindex` 工作流在 `NewWorkflow(ctx, config)` 阶段预编译 `compose.Runnable`
- `aiopsplan` 工作流在 `NewWorkflow(ctx, config)` 阶段预构建 `adk.ResumableAgent`

同时，`internal/bootstrap/app.go` 已同步改为在装配阶段传入 `ctx` 初始化这三个工作流。

## 2. 与需求的对应关系

对应 [001-工作流执行器预编译-需求.md](/home/ristial/projects/agent/OpsPilot/docs/requirements/001-工作流执行器预编译-需求.md)：

- “启动时构建一次、运行时复用”：已完成，三个工作流均改为在构造阶段缓存执行器
- “构建失败前移到启动阶段暴露”：已完成，`bootstrap.New(...)` 中初始化工作流时即可失败返回
- “保持对外接口不变”：已完成，对外 HTTP 路由和应用层调用语义未变化

## 3. 关键实现点

### 3.1 Chat 工作流

- 在 [workflow.go](/home/ristial/projects/agent/OpsPilot/internal/ai/workflows/chat/workflow.go) 中为 `Workflow` 增加 `runner` 字段
- 将 `NewWorkflow` 签名调整为接收 `context.Context`
- 在构造阶段调用 `buildRunner(ctx)` 并缓存结果
- `Chat` 和 `Stream` 改为直接使用缓存的 `runner`

### 3.2 KnowledgeIndex 工作流

- 在 [workflow.go](/home/ristial/projects/agent/OpsPilot/internal/ai/workflows/knowledgeindex/workflow.go) 中为 `Workflow` 增加 `runner` 字段
- 将 `NewWorkflow` 签名调整为接收 `context.Context`
- 在构造阶段调用 `buildRunner(ctx)` 并缓存结果
- `Refresh` 改为直接调用缓存的 `runner.Invoke(...)`

### 3.3 AIOps Plan 工作流

- 在 [workflow.go](/home/ristial/projects/agent/OpsPilot/internal/ai/workflows/aiopsplan/workflow.go) 中为 `Workflow` 增加 `planExecuteAgent` 字段
- 将 `NewWorkflow` 签名调整为接收 `context.Context`
- 新增 `buildAgent(ctx)`，集中完成 `planexecute.NewPlanner`、`NewExecutor`、`NewReplanner`、`planexecute.New`
- `Analyze` 中保留按请求创建 `adk.NewRunner(...)`，但不再重复构建 Planner / Executor / Replanner / Agent

### 3.4 Bootstrap 装配

- 在 [app.go](/home/ristial/projects/agent/OpsPilot/internal/bootstrap/app.go) 中统一改为 `NewWorkflow(ctx, config)`
- 启动期即可完成工作流构建校验

## 4. 已知限制或待改进点

- 当前未增加专门的性能基准测试，只通过代码路径和编译回归确认“重复构建已移除”
- `aiopsplan.Analyze` 仍然会为每次调用新建 `adk.Runner`，这是有意保留的轻量执行封装，不属于本次优化范围
- 如果未来需要按请求动态切换工具集或图结构，现有“启动时预编译”策略需要重新评估

## 6. 实现总结

这次改动是一次面向运行时效率和启动期可观测性的内部重构。它没有改变对外能力，但明确收敛了工作流的生命周期：

- 构建发生在启动阶段
- 执行发生在请求阶段
- 错误尽早在装配时暴露

这使得 `internal/ai/workflows` 的职责边界更清晰，也更符合仓库当前通过 `bootstrap.New(...)` 统一装配依赖的设计方式。
